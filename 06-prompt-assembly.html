场景：团队负责人在长会话中更新 AGENTS.md，要求从现在起遵守新的发布规则。

〔基于代码的推演〕下表按所引快照描述；Claude Code 的文档或 bundle 证据单独标注。

Harness 从用户操作到结果
Codex 比较指令快照 → 变化时发送替换或删除片段 → 新规则进入上下文。〔8〕
OpenCode 首次基线冻结 → 后续差异作为持久增量追加 → 避免整段基线每轮重发。〔13〕
pi / pi-durable coding-agent 对变化 section 发 patch；durable 按宿主传入的有序段比较 → 只记变化；不是自动读取任意文件。〔16〕〔18〕〔19〕
dsh 首次请求注入指令基线 → 读写时发现嵌套指令；动态目录与权限信息放 user 快照。〔21〕〔22〕
Hermes system 整会话冻结 → 压缩后重建并重读 memory；不能把写文件成功当立即刷新 system。〔26〕
OpenClaw 区分稳定前缀和动态后缀 → provider 按边界设置缓存标记；实际是否命中仍取决于服务端。〔29〕〔31〕
Claude Code 【bundle】context 做 memoize；【文档】子目录指令按需加载；此证据不足以承诺热更新延迟。〔34〕〔35〕
DeepAgents（1 月 Python） 传入 memory 文件源 → 启动加载到 system；自定义 system 与基础提示拼接，另装缓存 middleware；实时重载和命中率不能由此推定。deepagents@c177c9f:libs/deepagents/deepagents/graph.py#L113-L118；deepagents@c177c9f:libs/deepagents/deepagents/graph.py#L189-L237

为什么重要： 规则已写入磁盘不等于下一轮已采用。稳定前缀有助缓存，但实际计费改善必须看服务端 usage，不能从拼装顺序直接推出。

技术细节与出处

pi 的层次： agent-core 是循环与事件库；Bash、会话文件、自动压缩、技能和扩展等条目按引用归属 coding-agent；durable 是另一个持久运行时。下表的 10 月能力不能倒推为年初的库选型理由。

术语速读：step 是一次模型请求，turn 是一段任务；hook / middleware 是执行前后插入的业务逻辑；schema 是工具参数格式；checkpoint 是恢复检查点，journal 是已完成调用的结果日志；backend 是实际存储或执行后端；token 是模型计量文本的单位。

（压缩和计量见 07，记忆的存储与学习见 09，MCP 工具如何进入上下文见 08。）

共识

  • 组织方式相同： 都要把稳定指令、项目指令、技能目录、记忆、工具声明、环境信息（cwd、日期）、历史消息组织成一次请求。
  • 共同的缓存策略： 越多会话共享的内容放越前面，随目录、日期、本轮变化的内容放后面或者移出 system。这样稳定前缀才能复用，一次局部变化不会让整个前缀失效〔1〕〔2〕〔3〕。
  • 工具声明普遍独立于 system 文本（Codex 的 Responses Lite 是例外，见下表），并且多被当作单独的缓存位置处理〔4〕〔5〕。

关键差异

Harness 拼装顺序（可核对部分） 稳定/动态划分与缓存处理
Codex 普通 Responses：工具放独立的 tools 字段。Responses Lite：工具转成 developer AdditionalTools 前缀，再加 base instructions，整体插到 input 开头〔4〕。初始上下文先放显式 developer_instructions，再跑 thread contributors 和 turn contributors；AGENTS.md 从项目根到 cwd 依次串联（默认以 .git 定根，untrusted 项目不加载）〔6〕〔7〕 skills 和 AGENTS.md 都作为 world-state fragment：快照没变就不再发送，变化时发 replacement/removal〔8〕。memory 通过 developer policy 注入，V2 按每块最多 8,900 bytes 切分〔9〕。prompt_cache_key 优先用显式 override，内部子流程用 source:parent_thread_id，其他用 session_id〔10〕
OpenCode system 数组：agent.system（或内置 prompt）→ initial instructions。initial instructions 的顺序：CodeMode 目录 → MCP instructions → references → skills → 项目指令 → builtins（date→environment）→ entries。源码注释写明：从最多会话共享的内容排到最少共享的〔2〕〔11〕〔12〕 首次的 baseline 冻结，后续变化作为按时间排序的 durable delta 追加〔13〕。默认 cache 标记依次是最后一个 tool、system 首/末段、对话尾，总预算 4 个 marker〔5〕
pi coding-agent preamble → tools → rules → docs → addendum → project_context → skills → cwd → custom；customPrompt 会替换 preamble 并跳过默认的 tools/rules/docs；指令文件每目录取第一个命中：AGENTS.override.md → AGENTS.md → AGENTS.MD → CLAUDE.md → CLAUDE.MD〔14〕〔15〕 结构化 prompt 只对变化的 section 生成 patch；MCP 状态变化通过追加 section 进入对话〔16〕。Anthropic 下给初始 system、最后一个 tool、最后一条 user/system 的末 block 各打一个标记，不是每条历史都标记〔17〕
pi-durable sections 是调用方传入的有序数组，没有硬编码 coding-agent 那套顺序〔18〕 和已重放的 sections/tools 比较，只写 section patch 和 toolsAdded/Removed；tool_search 加载的工具在分支上一直保留，压缩后也保留〔19〕
dsh section 按 order 升序排列，order 相同按 name 排。中央分配的位置：identity -1000 → persona 前缀 0 → plan 500 → team 600 → 内置工具说明 1000–3000 → MCP servers 3100 → tools SDK 5000 → 结构化输出 9900 → harness source 10000 → persona 后缀 10200〔3〕〔20〕 动态 context（working directory 100、sandbox 110、approval 115 等）是 user-role 快照，代码注释写明“进程相关路径/端点不进入缓存的 system prompt”；渲染值不变就不发新消息〔21〕。AGENTS 基线在首次请求前进入，读写文件时再处理嵌套指令；skills 目录按 digest 去重，以 user message 发布〔22〕。工具默认按名称排序〔23〕
Hermes stable → context → volatile 三层：stable 包括身份、guidance、pinned skills；context 包括调用方 system_message 和项目 context files；volatile 依次是 skills index、memory、plugin sections、profile、timestamp、环境提示〔24〕〔25〕 三层输出缓存到 session，整会话冻结，压缩后才重建并重新加载 memory；日期只精确到天〔26〕。ephemeral system prompt 在 API 调用阶段追加到缓存的 system 之后〔27〕。Anthropic 默认 TTL 5m，最多 4 个 marker〔28〕
OpenClaw 身份 → 交互/执行 guidance → provider 稳定前缀 → 目录与工作区说明 → bootstrap → Project Context → SYSTEM_PROMPT_CACHE_BOUNDARY → 工具目录 → skills → memory → docs → sandbox → 动态后缀 → Runtime〔29〕〔30〕 稳定前缀的 cache key 是相关输入的 JSON SHA-256〔29〕；Anthropic payload 按 boundary 把 system 拆成两块，只有稳定块带 cache_control，然后先统计 system/tools 已用的 marker，剩余预算给 messages〔31〕
Claude Code 【bundle】systemContext（gitStatus 等）追加到 systemPrompt 之后；userContext 依次是 claudeMd、userEmail、attachedProject、currentDate，转成 <system-reminder> meta message 放在对话消息最前面；tools 单独传入〔32〕〔33〕。【文档】CLAUDE.md 加载顺序为 managed → user → project → local，子目录按需加载〔34〕 【bundle】context 做了 memoize；启用 boundary 时，boundary 前的正文合成 global scope，之后合成 org scope〔35〕。【文档】plugin skill 的名称和描述常驻上下文，正文使用时才加载〔36〕

指令文件预算（单位各不相同）： - Codex：项目指令默认 32×1024 bytes，超出截断〔37〕； - Hermes：指令字符预算 min(500000, max(20000, context×4×0.06))〔38〕； - OpenClaw：bootstrap 单文件 20000 chars、总计 60000 chars，USER.md 固定 4000 chars〔39〕； - dsh：单文件默认 1048576 bytes，base 装配总预算 65536 bytes，单文件超限时整份忽略而不是截断〔40〕。

缓存保留时长： - pi：Anthropic 默认 short，可选 long（支持时 TTL 1h）〔41〕； - Hermes：支持 5m/1h/auto/off〔42〕； - OpenCode：Anthropic 支持 1h〔42〕。

以上都只是提高命中机会的设计，不保证服务端一定命中。

对不同用户的影响（基于控制流的情景推演）

  • 成本敏感用户： 日期、cwd 这类会变的内容放在哪里，决定了换天或换目录时缓存前缀会不会整体失效。OpenCode 把 date/environment 放在 baseline 末尾；dsh 把路径类 context 移出 system；Hermes 冻结整个会话的 system，日期只精确到天，而且要等上下文重建时才更新〔12〕〔21〕〔26〕。
  • 扩展作者： 在 prompt 中段插入动态内容，会破坏后面所有内容的缓存。OpenClaw 的 boundary 和 dsh 的位置表都给出了“该插在哪”的约定〔29〕〔20〕。社区有 pi 扩展注入的 prompt 丢失、导致整段重新计费的报告（见 18）。
  • 企业团队、monorepo： 指令发现规则不同：Codex 不越过项目根，pi 扫描祖先目录，dsh/OpenCode 在读写文件时懒加载子目录的指令。规则文件在磁盘上存在，不等于进入了请求〔7〕〔15〕〔22〕。
  • 重度用户： Hermes 写入记忆后，当前会话的 system 仍是旧的快照；Codex 的 world-state 快照有变化才发增量。所以“已记住”和“下一次请求能看到”之间会有延迟〔26〕〔8〕。

面试可讲的点

  1. 按共享程度排序： “从跨会话共享到本轮专属”是各家共同的排序原则，可以直接作为 prompt 拼装的设计原则来讲（OpenCode 源码注释写得最明确）〔2〕。
  2. 增量还是整段重发： Codex world-state、OpenCode durable delta、pi section patch 都只发变化的部分，可以量化成“每轮重发的 system token 数”〔8〕〔13〕〔16〕。
  3. 缓存指标： 缓存命中率和“每轮新增的未缓存 token”可以作为 prompt 改动的护栏指标，避免一次改动让所有会话的缓存失效。注意源码只能证明“命中机会”的设计，不能证明服务端实际命中了。
