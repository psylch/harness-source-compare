11 · 持久化与恢复：保证要落在失败窗口上

← 10 · 多 agent 策略：从 Kimi /tower 到各家编排 · 总览 · 12 · 扩展性：能看到 ≠ 能改，能改请求 ≠ 能换 loop →

（pi-durable 的逐层拆解见 13 · pi-durable。）

共识

  • 各家都保存有序状态： Codex rollout、dsh 日志、OpenCode bus、pi-durable Storage。

  • 但防的失败窗口不同：

    • Codex：文件 flush；
    • dsh：调用前 checkpoint；
    • OpenCode：inbox 事务；
    • pi-durable：任务 checkpoint。

    所以不能按 JSONL 还是 SQLite 这种扩展名给可靠性排序〔1〕〔2〕〔3〕〔4〕。

  • “先存后显示”不是某一家独有的：

    • Hermes：tool result 的 callback 在 flush 之后才调用；
    • OpenCode：tool call 在执行前持久化，stream event 按 100ms 批量写；
    • dsh：关键动作前的 checkpoint 是 fail-closed 的〔5〕〔6〕〔2〕。

关键差异

Harness 存储、路径与分支 崩溃恢复、幂等与写者边界
Codex CODEX_HOME/sessions/YYYY/MM/DD/rollout-…jsonl；写入有 flush，但这条路径不 fsync；fork 复制指定边界之前的 history〔1〕〔7〕 daemon handoff 先 persist_thread 再记 interrupted snapshot，重启后正常 cold resume；有条件：regular、未 cancel、单一 local environment，remote 等情况排除。恢复的不是任意工具的程序计数器〔8〕
dsh 日志放在 root/projectKey/encoded session ID 下；JSONL 默认 zstd 压缩；base 装配实际安装了 checkpoint-policy；普通 storage batch 默认 200ms〔9〕 在调用 LLM、顶层 tool、pre-step 之前 flush，失败就阻止继续；恢复时补上未完成的 tool/step/turn closers；有 torn-tail repair 和 fsync 路径；跨进程写者锁用 POSIX flock / Windows semaphore，进程退出由内核释放〔2〕〔10〕
OpenCode SQLite 中 aggregate event 和 projection 在同一事务里写；fork 只取已 settled 的部分〔3〕〔11〕 inbox ID 在同 session/type 下先写者胜出；消费 inbox 和插入消息在同一事务。restart 默认 10 次，明确是 at-least-once，不是 cluster fence；未 settled 的 tool 标为失败，后台 shell 重启后标为取消〔12〕
Hermes profile 下的 state.db，SQLite WAL、BEGIN IMMEDIATE；用 persisted-marker 避免重复写 message〔13〕 执行 tool call 前先 flush，flush 失败就不执行；session facade 的跨进程 lease 每 60s 刷新一次，失去 lease 就中断〔14〕
OpenClaw legacy sessions.json 映射到 openclaw-agent.sqlite；native session manager 维护 snapshot、writer fence 和 branch epoch；Codex harness 另外绑定远端 thread ID〔15〕 fence/epoch 会拒绝 stale snapshot；基础 session 只有 user message_end 走 publishAfterPersistence，其他事件可能先 emit 再 persist〔16〕
Claude Code 【bundle】~/.claude/projects/<sanitized cwd>/<sessionId>.jsonl，子 agent 另存 subagents/agent-ID.jsonl；用 parentUuid / isSidechain 表示链；写入队列 flush 间隔 100ms〔17〕 【bundle】某个 subagent 分支 await store 之后才 yield，但 catch 会吞掉存储异常〔18〕。【文档】每个起始 prompt 做一次 checkpoint，保留最近 100 个，默认在最后一次保存约 30 天后清理；Bash 修改的文件不跟踪，turn 中途不新建 checkpoint〔19〕
pi coding-agent JSONL append-only 树，用 id/parentId 和 leaf 表示分支；默认路径 ~/.pi/agent/sessions/<encoded-cwd>/…jsonl〔20〕 恢复的是会话树，和 pi-durable 是不同的包、不同的存储合同〔20〕〔4〕
pi-durable Storage 承诺 atomic commit 并返回 Seq；有 SQLite / JSONL / Memory / Cloudflare 几种 adapter〔4〕〔21〕 恢复单位包括 task checkpoint、generation phase、tool intent、codemode journal；requestId 只用于入队去重；不提供跨进程写者锁〔22〕

对不同用户的影响（基于控制流的情景推演）

  • 企业团队： 创建工单成功了，但结果写盘前断电。requestId 去重只能保证用户输入不重复入队；pi-durable 默认按 unsafe 恢复，会报告 interrupted。要靠工单服务自己的业务幂等 key，不能宣传端到端 exactly-once〔22〕。
  • 非工程师： 点了发送，网页重连后又发了一次。pi 的 requestId 和 OpenCode 的 inbox ID 都能返回原来那次提交；但如果是不同的 ID，就会算成两条输入〔22〕〔12〕。
  • 扩展作者： 两个 worker 同时接管同一个会话。dsh 的 OS 锁可以拒绝第二个写者；pi-durable 的宿主如果创建了两个 Session 实例，实例内的队列不能互斥〔10〕〔22〕。
  • 成本敏感用户： Codex cold resume 省的是重新手动组织任务，pi journal 省的是重复执行已完成的调用。两者优化的是不同的东西〔8〕〔23〕。

面试可讲的点

  1. 先问“外部操作成功、结果还没 commit 时崩溃怎么办”，比问“有没有 resume”更有区分度。
  2. 恢复率指标要按失败窗口分别统计：模型请求中途、工具执行中途、结果写盘前。
  3. 单写者是部署层的问题：dsh 在内核层用锁解决，pi-durable 交给宿主。做 HA 部署之前要先设计 owner/fencing。
