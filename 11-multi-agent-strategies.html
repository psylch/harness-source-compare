场景：工程负责人让多个 agent 同时改一个仓库，准备把结果合并为一次发布。

〔基于代码的推演〕下表按所引快照描述；Claude Code 的文档或 bundle 证据单独标注。

Harness 从用户操作到结果
Codex V2 默认继承父上下文 → 共用工作区；spawn 路径没有自动 worktree → 父级负责集成检查。〔13〕
OpenCode fresh 子会话 → 提示词约束文件使用 → 父级验收；提示不是强制文件锁。〔2〕
pi / pi-agents pi-agents 文档提供 DAG 与消息，不自动隔离工作树；它是独立项目，不能当成 pi 核心默认。〔15〕
dsh 可用 team 分工和任务依赖 → Lead 集成；文档明确把 worktree 策略留给部署层。〔14〕
Hermes 子任务执行 → 可选 worktree，默认关闭 → 不开启就不能假设文件隔离。〔16〕
OpenClaw 按树状关系交付 → 可选 worktree → 父级验收。〔17〕
Claude Code 【文档】可选 worktree；teams 可用 hook 打回未达标交付 → 要显式配置规则。〔12〕
DeepAgents（1 月 Python） task 隔离对话并回传最后消息；其他非排除状态也可回传 → 不等于独立文件系统或代码合并门禁。deepagents@c177c9f:libs/deepagents/deepagents/middleware/subagents.py#L365-L393
Kimi /tower 建立 worktree 与租约 → worker 执行 → review 与范围等代码门禁通过才合并。〔8〕〔9〕

为什么重要： 任务完成不等于改动可合并。要看谁负责隔离文件、检查范围、复核结果；否则并行节省的时间会在集成时补回来。

技术细节与出处

pi 的层次： agent-core 是循环与事件库；Bash、会话文件、自动压缩、技能和扩展等条目按引用归属 coding-agent；durable 是另一个持久运行时。下表的 10 月能力不能倒推为年初的库选型理由。

术语速读：step 是一次模型请求，turn 是一段任务；hook / middleware 是执行前后插入的业务逻辑；schema 是工具参数格式；checkpoint 是恢复检查点，journal 是已完成调用的结果日志；backend 是实际存储或执行后端；token 是模型计量文本的单位。

（各 harness 内建子 agent 的默认值见 10。本页证据分级：[源码] 带 repo@sha:path#行号；【文档】 是官方文档或 changelog，属于厂商说法；[社区] 是 X 帖子或 issue，只代表发帖人的经验。Kimi 源码快照为 MoonshotAI/kimi-code@18c6d64，…/ 表示 packages/agent-core-v2/src/features/ 之下的路径。）

共识

  • 子 agent 用独立上下文，默认不继承对话，fork 作为可选项。Claude Code、Cursor、OpenCode、pi-agents、Manus 默认 fresh〔1〕〔2〕。
  • 交付物就是子 agent 的最后一条消息。 Claude Code、Kimi worker、dsh 都明确写了“最终消息就是全部交接”〔3〕。
  • 后台运行加完成通知，禁止轮询。 OpenCode、Kimi tower、pi-agents 的提示词或机制里都写了“不要 sleep 或 poll”〔2〕〔4〕。
  • 深度和并发都有上限，但数值各不相同：深度 1–5，并发 4–20，扇出最多 128。

关键差异

Kimi /tower：把 PR 流程写进代码 [源码]

  • 入口： 需要实验开关，加上 /tower on。只有主 agent 能进入 tower 模式，同一工作区同一时间只能有一个 live session 拥有 tower；和 plan / swarm / goal 三种模式互斥〔5〕。
  • 角色： tower 自己不写 mission 代码；worker 的工具白名单里没有 TowerSpawn 和 TowerMerge，所以不能派工、不能合并〔6〕。
  • mission 模型： 字段包括 kind（build/survey）、scope（glob）、branch、worktree、deps、status、tasks[]；用户原话放进 context，不塞整段对话〔7〕。
  • 隔离： 先拿分支租约，再 addWorktree；bash guard 对解析不了的危险命令一律拒绝〔8〕。

  • merge gate（由代码执行）会拒绝以下情况：

    • mission 未完成，或还有未完成的 task / blocker；
    • worker 状态未知（“unknown 不等于 idle”）；
    • 分支落后于 base；
    • 最近一次 review 不 clean；
    • review 之后又有新提交；
    • 改动超出 mission scope。

    每个 reviewer 最多 5 轮〔9〕。

  • 并发： 预算上限 TOWER_MAX_BUDGET = 16；遇到限流时每 2 秒减 1、最低减到 1，180 秒后恢复〔10〕。

  • /swarm 是另一回事： 用模板加 {{item}} 扇出，最多 128 个子 agent，没有 worktree、merge gate 和 review 闭环，是 map 式的并行〔11〕。

真正的分歧有四个：

  • 默认上下文：
    • fresh：父级必须写好 brief，省 token；
    • 继承全部（Codex v2）：子 agent 立刻懂背景，但成本随父上下文增长；
    • 代码生成 brief（Kimi tower）：介于两者之间，可以审计〔13〕〔7〕。
  • 文件冲突由谁负责：
    • harness 强制（tower）；
    • 可选隔离（Claude、Hermes、OpenClaw）；
    • 有意不管（dsh 文档论证 branch 命名、merge 策略、cleanup 都属于部署层的决定）〔14〕。
  • “完成”由谁判定： 代码 gate、hook gate（Claude teams 中 TaskCompleted 返回退出码 2 可以打回）、或者父模型自己判断〔9〕〔12〕。
  • 通信拓扑： 只回父级，还是 peer mailbox。pi-agents 明确不设跳数上限，“两个被告知持续交谈的 agent 会一直聊到你停下其中一个”〔15〕。

对不同用户的影响

  • 独立开发者，在一个仓库里并行写功能： tower 最接近“交给一个 tech lead”，但 token 消耗大；Claude 加 isolation: worktree 更轻；Codex 子 agent 默认共享工作区。
  • 调研、review、排查： Claude subagents/teams、Cursor Explore、Manus Wide Research 更合适，不需要 worktree。Manus 官方自己列出的不适用场景是“有顺序依赖的任务”和“少于 10 项”〔18〕。
  • 大批量同构任务： Kimi swarm（最多 128 个）〔11〕。
  • 自己搭 harness 的工程师： dsh 的 provider 可插拔，可以把真实的 Codex 或 Claude Code 当 worker；pi-agents 提供 durable 和 DAG〔14〕〔15〕。
  • 社区经验 [社区]：
    • “同时跑超过 2 个子 agent，几乎必然是烧 token 换不来质量”；
    • “1 个 orchestrator 配 1 个 executor 目前最好”；
    • tower 用户反馈规划、隔离执行、review、修复、再 review 这一套“消耗非常快”〔19〕〔20〕。

面试可讲的点

  1. 多 agent 的瓶颈已经从“能不能并行”变成“怎么验收、怎么合并、怎么看得见”。tower 用代码 gate 兜底，dsh 公开论证不在团队层做 worktree，这是两种产品哲学。
  2. 默认上下文的选择直接影响 issue 里“token 失控”问题出现的频率（Codex 默认继承全部 vs Claude 默认 fresh 但 fork 共享缓存）〔13〕〔12〕。
  3. 可以讲的指标：子 agent 交付的首次合并率（gate 首次通过率）、review 轮数、每个 mission 的 token、死亡与 resume 的比例、因 scope 越界被拒的次数。把协议状态落盘，这些指标就能直接从协议日志里算出来。指标框架见 17。
