13 · pi-durable：从一次用户提交到 codemode 恢复

共识

  • 核心做法： pi-durable 把对话、任务和程序内可记录的调用放进同一套提交与恢复规则，四个环节连成一条可检查的恢复链：
    • Storage 原子 commit；
    • running 的 task 重启后改回 pending；
    • 工具先提交 intent 再执行；
    • codemode 的结果先写 journal 再投递〔1〕〔2〕〔3〕〔4〕。
  • 和其他家的关系： “先存后显示”其他家也有（见 11）。pi-durable 更突出的地方有两点：把这些边界统一成可恢复的 task/document 模型；把 codemode 程序的调用序列纳入回放。
  • 它和 pi coding-agent 的会话树是两个包，存储合同也不同。 它也不是 CLI 上给所有会话自动打开的一个开关〔1〕〔5〕。

关键差异：逐层边界

边界 实际数据与调用顺序 能保证 / 不能保证
Storage 接口 commit(writes) 原子接受一组 StorageWrite，返回 Seq；Session 用 promise tail 串行执行 commit；SQLite 有 conversations / entries / tasks / submissions / documents / document_revisions 等表〔1〕〔6〕〔5〕 原子性是 adapter 必须兑现的合同；Session 串行不等于跨进程互斥〔7〕
输入去重 按 conversation/requestId 查已有的 submission：同 type 返回原 ID 并忽略新 payload，type 冲突则抛错；durable inbox 记录 queued steer/followUp，默认 followUp〔8〕 浏览器重试只会入队一次；同一 ID 改了文本也不会更新旧提交；不覆盖模型请求的计费和外部 effect〔8〕〔3〕
task / generation scheduler 启动时把 running task 转为 pending 并保留 checkpoint；generation 分别检查 prepare / request / retryWait / poll / tools 几个阶段；最终 assistant message 和后续 tool tasks 在同一个 commit 里建立〔2〕〔9〕 恢复的是显式持久化的状态机，不是整个 JS 堆或网络 socket〔10〕
先存后显示 #runCommit：settle writes→await storage.commit→tx.adopt(seq)→#publish；partial generation 默认 100ms 节流，同一时间只有一个 commit in-flight〔11〕 committed 事件消费者看到的状态已被 adapter 接受；“每个 token 都立即落盘”不成立〔11〕
tool intent 与重试 参数验证→hooks→再次验证→先 commit {phase:execute, arguments, replay}，默认 replay=unsafe，然后才执行；恢复时只有持久策略和当前策略都是 safe 才重跑，否则返回 interrupted〔3〕 safe 是工具作者声明可以重试，不是框架证明“只执行了一次”；外部服务的幂等 key 仍然需要
codemode 启动 checkpoint 先生成 seed/now，把 version、tools、namespaces、globals、store、deadline 和 start 一起 commit；重启时已有 done 就直接复用；版本或 deadline 不兼容则拒绝继续〔12〕 脚本可以从头重新执行到已知边界，前提是恢复环境和调用轨迹兼容
确定性与 journal VM 提供 seeded PRNG、虚拟时钟和 WASI random_get，环境固定为 UTC；比对调用 fingerprint、name/args、issuedAfter，按记录顺序投递结果；结果先 commit 到 journal 再 deliver〔13〕 已完成的 nested call 按 journal 复用，未完成的仍按 safe/unsafe 策略处理；并发调用的完成顺序也会被记录
fork / 分支 fork 以 entry.commitSeq 作为 asOf；agent doc 可以 rewind，provider doc 用 initial 重新生成 ID〔14〕 fork 不会撤销已经发生的外部副作用
单写者与介质 README 明确要求 single writer、没有跨进程锁；SQLite 使用 WAL + synchronous NORMAL；JSONL 默认 fsync=false〔7〕〔15〕 不能声称 pi-durable 已有跨进程单写者锁，也不能声称所有 commit 都已 fsync

与其他三种恢复路线的取舍：

路线 首先解决的体验 不应因此承诺的能力
dsh 日志为准 重建模型可见历史，动作前 flush，恢复时补 closers，用 OS 写者锁防竞争〔16〕 不自动回滚外部操作，不等于 codemode 的 journal 回放
Codex daemon 跨重启交接符合条件的 interrupted turn〔17〕 cold resume 不保存外部程序或工具栈，remote 环境被排除
Claude checkpoint【文档】 按 prompt 节点回退对话和被跟踪的文件改动〔18〕 不跟踪所有 Bash 编辑，不是外部操作的 undo
pi-durable / codemode 持久 task 和程序调用 journal 衔接起来〔3〕〔4〕 没有内建跨进程锁；requestId 去重 ≠ effect exactly-once；fork ≠ 撤销现实世界

对不同用户的影响（基于控制流的情景推演）

  • 长任务重度用户： 脚本并行读 200 份报表，读到第 160 份时进程崩溃。如果前面的 nested results 已经提交到 journal，重跑时会直接消费旧结果再继续；只做聊天 resume 的实现恢复不了脚本里的局部变量〔4〕〔13〕。
  • 企业团队： 工具作者把“创建工单”错误地标成 safe，恢复时可能会重复建单〔3〕。
  • 成本敏感用户： 代价同样具体：checkpoint/journal 写入更多，流式显示要等 commit，回放要求代码、指纹和调用顺序兼容，unsafe 的未完成工具可能要人工核对〔11〕〔12〕。

面试可讲的点

  1. 它最适合进程寿命短于任务、一个模型工具内部含很多调用的场景；pi-durable 也提供 Cloudflare adapter〔1〕〔5〕。
  2. 进程崩溃恢复和突然断电要分开测：SQLite NORMAL 和 JSONL fsync=false 提供的是不同的承诺〔15〕。
  3. 常见的误读要纠正： - “同 requestId 不会重复执行”应该说成“同 conversation/type 的提交只入队一次”； - “有单写者锁”不成立〔8〕〔7〕。
