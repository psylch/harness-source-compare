15 · DeepAgents → pi-agent-core 决策分析

场景：Vida 的后台目标还在推进，用户突然说“别发给客户，先给我看”

源码支持的迁移理由是：把产品的执行规则、个人上下文和交互状态掌握在自己的运行时中。代价是团队要接手持久化、审批、压缩、调度和可观测性。 这不是“pi 天生更可靠”的结论。

已知背景：Charles 于 2026.01–2026.06 在 Einsia 担任 Agent PM；Vida 是主动式工作 agent，包含 Goal、Routine、macOS AX（辅助功能接口）个人上下文采集与记忆，以及 OpenChronicle。Charles 确认比较对象是嵌入产品的 DeepAgents 与 pi-agent-core。实际使用版本、故障、决策过程和收益仍需他确认。

〔基于代码的推演〕年初 pi-agent-core 在当前工具结束后读取 steer() 队列，跳过尚未执行的同批调用，再把新消息交给模型；followUp() 则等本轮任务原本要结束时处理。DeepAgents JS 的 interruptOn 是指定工具前的人工审批，可用同一 thread 的 Command({resume: ...}) 恢复。前者更直接表达“改方向”，后者更直接表达“先审批”；两者都不能撤销已发送的邮件。〔P1〕〔D1〕〔D2〕

对 Vida 的含义〔推断〕： 用户插话、Routine 触发、AX 更新应是不同类型的输入；哪些立刻改变方向、哪些只更新背景、哪些等当前目标结束，由产品决定。如果这正是当时的主要难题，pi-agent-core 的小循环与显式队列是合理理由；若首要需求是审批暂停后跨进程恢复，DeepAgents 的现成接口更有优势。

10 月变化：只用于说明演进

〔源码已核实〕pi c268154 的 agent-core 默认并行；某工具声明 sequential 会使整批串行。steering 改为当前 assistant 的工具执行完成后采纳，不跳过当前批次；新增 beforeToolCall、afterToolCall 等接口。年初“每个工具后插话并跳过剩余工具”的体验不能无测试升级。〔H3〕

〔源码已核实〕DeepAgents JS HEAD 使用带 backend、按模型 profile 计算默认值的摘要 middleware，并有自定义 middleware 合并/排除、可选异步子 agent 桥；仍将 checkpointer/store 传给 createAgent。Python HEAD 也保留此构建方式，并明确异步子 agent 支持 LangSmith 部署。不能把年初固定 170000 token 的限制写成所有后续版本都如此。〔H1〕〔H2〕

〔源码已核实〕coding-agent 的会话文件、压缩实现、扩展系统在年初仓库已经存在，但属于 packages/coding-agent，不是 agent-core 自动拥有的功能。10 月的 pi-durable 是独立包；packages/durable 的目录历史从 2026-09-18 的 080160162 开始，年初树不存在该目录，因此其 codemode journal、请求去重、持久任务都不能解释 1–2 月的 agent-core 选型。目录首次出现不等于所有相关思想的最早发明时间。〔P7〕〔H4〕

DeepAgents 做得更好，以及迁移必须支付什么

DeepAgents 年初就把规划待办、文件读写、长输出外置、子任务和自动摘要组合起来；checkpointer/store 与工具审批已有连接点。如果产品工作流接近这些默认假设，团队可以少写相当多的基础设施。它允许自定义 middleware，所以“框架完全不可定制”也不成立。〔D1〕〔D2〕〔D4〕〔D6〕

〔推断〕迁到 pi-agent-core 的收益应是减少不需要的默认行为、让产品拥有上下文和执行规则，而不是减少所有代码。必须重做或对接：历史消息格式、工具 schema 与错误转换、持久队列、恢复协议、审批状态、摘要和文件索引、子任务管理、可观测性、权限与数据保留。已有 LangGraph 状态和 checkpoint 不会直接变成 Agent.messages；双运行时迁移期间还要处理旧会话恢复与副作用去重。

〔推断〕合理的决策门槛是：产品确实需要长期维护自己的 Goal/Routine/个人上下文模型，并有能力承担这些基础设施；否则 DeepAgents 的现成能力可能更划算。可先用同一组“插话、重启、重复触发、长上下文、模型切换”任务对照，保持工具与模型相同，分别看质量、延迟、成本和恢复结果。这里是建议的验收方案，不是已完成实验。

需要 Charles 确认

  1. 实际迁移日期、DeepAgents 是 JS 还是 Python、两边版本或 lockfile、试验与生产是否一致。
  2. 当时最痛的三个坏例：插话延迟、上下文难控制、调试困难、成本，还是别的问题？哪些有记录？
  3. Vida 宿主是否 TypeScript；Goal、Routine、AX、OpenChronicle 各自由哪个服务负责，是否已有会话/任务存储。
  4. 实际用过哪些 middleware、文件 backend、checkpointer、HITL、子 agent、LangSmith；哪些是迁移后必须补回的。
  5. pi-agent-core 是否被 fork，是否自建并发、审批、摘要、持久化；升级时是否注意 steering 语义变化。
  6. 同任务对照的模型、成本、成功率、P95 插话延迟、坏例定位耗时，以及样本量和观察周期。
  7. 迁移是否完成、灰度比例、耗时、回退条件；“预期收益”与“观察结果”分别是什么。
