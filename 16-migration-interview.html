一页讲述：产品问题 → 评估 → 决策 → 结果

我在 2026 年 1 月到 6 月担任 Einsia 的 Agent PM，做的是 Vida，一个主动式工作 agent。产品包含 Goal、Routine、macOS AX 个人上下文采集和记忆，以及 OpenChronicle。用户不只是发一条指令等回答，还需要让目标持续推进、按 Routine 发起工作，并随时改变方向。

我推动团队从 DeepAgents 转向 pi-agent-core。这里比较的是嵌入产品的 agent 运行时库。我们当时使用的 DeepAgents 语言、版本和迁移时间是【待 Charles 确认】。最关键的产品问题是【待 Charles 确认：一个真实坏例，以及它影响了哪些用户】。

我会把评估拆成三个问题：第一，用户插话之后，下一步动作何时真正改变；第二，AX 和个人记忆由谁筛选后送给模型；第三，任务重启后，恢复和副作用由谁负责。实际采用的评估任务、参与人和取舍顺序是【待 Charles 确认】。

源码支持这样的技术解释：年初 pi-agent-core 有 steer、followUp、上下文转换和事件接口，能让产品层直接定义输入优先级、上下文策略和交互状态；它依赖 pi-ai 统一模型调用。DeepAgents 则提供待办、文件后端、子 agent、摘要以及检查点和审批接口。如果团队已经决定自己维护 Goal/Routine 和个人上下文，选择更小的循环，有利于把这些规则放在产品层。这是对选型理由的重建；它是否就是当时最重要的理由，需要我补上【待 Charles 确认：决策记录或具体例子】。证据见决策分析的 P1–P6、D1–D6。

这个选择有明确代价：pi-agent-core 不自动提供持久会话、定时调度、摘要或完整审批系统。我们实际补了【待 Charles 确认】，用了【待 Charles 确认：人力与时间】，对旧会话和外部副作用采用【待 Charles 确认：迁移及回退方案】。DeepAgents 在这些现成能力上有优势，所以我不会把它描述成“做不到”或“只能用 Python”。

预期收益是更清楚的执行控制、更合适的个人上下文和更容易定位坏例。实际观察结果是【待 Charles 确认：指标、基线、改后值、样本量、观察周期】；如果没有可靠数据，我只讲交付了什么、解决了哪个可复现坏例，不把预期写成已经提升的百分比。迁移是否全面完成、哪些场景仍有问题是【待 Charles 确认】。

被追问时的三个准确边界

  • “是不是因为 pi 有 durable？” 年初 agent-core 不包含 pi-durable；年初仓库的 CLI 会话、压缩和扩展也属于 coding-agent 层，不能当成这次库选型的原生收益。
  • “是不是 pi 更快、更便宜？” 源码只能支持控制点与依赖结构的差异。速度和成本要用相同任务、模型与工具的结果证明，数据是【待 Charles 确认】。
  • “为什么不继续定制 DeepAgents？” 它支持 middleware 和 backend 定制。应解释当时最难适配的业务规则及总维护成本：【待 Charles 确认】，而不是声称框架不可扩展。

上述技术边界与版本依据见决策分析；具体经历保留空位，确认后再用于面试。
