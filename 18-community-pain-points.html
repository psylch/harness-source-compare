证据性质：GitHub issue 和 X 帖子代表报告者的经验，不是经过复现的缺陷结论；括号里的 👍 和评论数是收集时的快照。issue 时间窗约为 2026-09-05 至 10-16。“roadmap 优先级”一列是 PM 判断。

共识

  • 痛点集中在“看不见”和“控不住”：
    • 状态显示不对；
    • 压缩什么时候发生、丢了什么不知道；
    • 成本突然暴涨；
    • 子 agent 卡住或重复投递。
  • 这些都是 harness 层的问题，不是模型能力问题。 每一类都能对应到前面某一层的具体设计。

对不同用户的影响

  • 长任务重度用户： 受压缩和状态错误的影响最大（#98747、#37729 一类）。
  • 成本敏感用户： 受轮询重计费和子 agent 放大的影响最大（#46023、#37299），对应 X 上 “超过 2 个子 agent 几乎必然烧 token” 的经验 社区。
  • 企业团队： 受 daemon 默认开启、默认 “Always allow” 的影响最大（#48195、#102136）。
  • 扩展作者： 受跨端不一致的影响最大（#99045、#10281）。

面试可讲的点

  1. 排优先级的逻辑： 先修“看不见”（压缩、用量、状态），再修“控不住”（成本熔断、授权降级），最后做“更多”（跨 harness 兼容、多 agent 工作台）。前两类直接决定 17 里的信任护栏。
  2. 用一个 issue 讲一条完整的 PM 闭环： 以 #98747 为例： - 现象：空闲压缩静默丢弃上下文； - 根因层：压缩触发和可见性，见 07； - 方案：压缩前预览、可撤回、可关闭，日志记录真实的触发原因； - 指标：压缩后任务失败率、压缩后重复读取次数； - 发布：灰度上线，护栏是回滚率。
  3. 英文社区沟通： 回复 issue 时先确认复现条件和版本（例如 #98747 标注了 2.1.286），再给 workaround 和 roadmap 状态。
